---
title: 'Webhook Secret Rotation'
description: 'Rotate the webhook signing secret without losing a delivery: the 7-day overlap window.'
---

Your endpoint verifies webhook signatures with the key's webhook secret. Rotate it when someone with access leaves, when it may have leaked, or as routine hygiene. Rotation has a **7-day overlap** in which deliveries are signed with both the new and the previous secret, so nothing in flight fails verification.

## Rotating

```bash
curl -X POST https://api.kash.bot/v1/auth/api-keys/me/webhook-secret/rotate \
  -H "X-API-Key: $KASH_API_KEY"
```

The call rotates the secret of the key that makes it, and needs the `webhooks:manage` scope. Send no body.

Response `200`:

```json
{
  "webhookSecret": {
    "secret": "whsec_…",
    "rotatedAt": "2026-10-20T12:00:00.000Z",
    "previousRetainedUntil": "2026-10-27T12:00:00.000Z"
  },
  "data": { "…": "same as webhookSecret" },
  "_meta": { "requestId": "…", "timestamp": "…", "message": "…" }
}
```

The new `secret` is shown **once**. Store it before doing anything else. The response carries `Cache-Control: no-store`.

With the SDK: `await kash.webhooks.rotateSecret()`.

### 60-second cooldown

A second rotation within 60 seconds of a successful one is refused with `429 WEBHOOK_SECRET_ROTATION_COOLDOWN`, and `Retry-After` counts down the rest of the cooldown.

The cooldown protects you from a retry storm. If your client timed out on the first rotation and retried, a second rotation would replace the previous-secret slot with a secret you never saw, and lose the secret your endpoint still trusts.

**If you lost the response to a rotation, don't rotate again.** Contact [support@kash.bot](mailto:support@kash.bot) with the API key's id.

## During the overlap

Until `previousRetainedUntil`, every delivery's `X-Kash-Signature` carries two `v1=` values, one per secret:

```
X-Kash-Signature: t=1792000000000,v1=<hmac-with-new-secret>,v1=<hmac-with-previous-secret>
```

A verifier that accepts the request when **any** `v1=` matches (the SDK and every [reference implementation](/developer-docs/rest-api/webhooks/verifying) do) keeps working whichever secret it holds. After `previousRetainedUntil`, only the new secret signs.

## Recommended rollout

1. Rotate and capture the new secret.
2. Deploy your endpoint with the new secret. If your verifier accepts any matching `v1=`, that is all you need; otherwise configure both secrets and accept either.
3. Remove the previous secret from your configuration any time before `previousRetainedUntil`.

## What can go wrong

**"I switched my verifier to the new secret straight away."** Fine: deliveries during the overlap carry a signature for each secret, so the new one matches.

**"I lost the new secret, but my endpoint still has the old one."** Your endpoint keeps verifying until `previousRetainedUntil`. Don't simply rotate again: a second rotation makes the lost secret the "previous" one, and the old secret your endpoint holds stops signing at once. Rotate again only when you are ready to deploy the result immediately, or contact [support@kash.bot](mailto:support@kash.bot).

**"Verification started failing a week after rotating."** The overlap ended and your endpoint still had only the previous secret. Configure the current one. `GET /v1/account/usage` shows the failures in `webhooks["7d"].failed`.

There is no endpoint that reads a secret back: after the rotation response, the plaintext exists only in your configuration.
