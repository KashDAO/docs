---
title: 'Webhooks Overview'
description: 'Receive trade lifecycle events at your endpoint: HMAC-signed, retried and replayable.'
---

Webhooks tell your code when something happens to a trade: it needs confirmation, it completed on chain, it failed, or it was rejected. They replace polling `GET /v1/trades/{id}`.

## Setting it up

Each API key can have a webhook URL. Set it on the key in the Kash app under **Settings → API Keys**. Events for trades placed with that key are POSTed to that URL. The key's signing secret is shown once when it is created, and can be [rotated](/developer-docs/rest-api/webhooks/secret-rotation).

The URL must be publicly reachable. Redirects are not followed, so register the final URL.

## Events

| Event                         | When | `data.status` |
| ----------------------------- | ---- | ------------- |
| `trade.confirmation-required` | A high-value trade is waiting for `POST /v1/trades/{id}/confirm` (the create call returned `202`). | `pending_confirmation` |
| `trade.completed`             | The trade executed on chain. | `completed` |
| `trade.failed`                | The trade failed during execution. | `failed` |
| `trade.rejected`              | The trade was refused before execution, for example by the daily spending cap or another risk check. | `rejected` |

## Envelope

```json
{
  "id": "6f1c2a3b-9d0e-4f7a-8c1b-6e5d3f4a2c9b",
  "type": "trade.completed",
  "apiVersion": "2026-08-19",
  "createdAt": "2026-10-20T12:34:56.789Z",
  "data": { }
}
```

| Field        | Use |
| ------------ | --- |
| `id`         | The event id (a UUID). **Deduplicate on this.** Same value as `X-Kash-Event-Id`. |
| `type`       | The event name. Branch on it. |
| `apiVersion` | Always `2026-08-19`: webhooks use that contract, so payloads carry `chainRef` and Solana signatures. |
| `createdAt`  | When the event was created. It is the same on every retry and replay. |
| `data`       | The event payload, below. |

### Common payload fields

Every `trade.*` payload carries:

| Field          | Notes |
| -------------- | ----- |
| `tradeId`      | The trade's `id`. |
| `marketId`     | |
| `chainRef`     | For example `solana:mainnet-beta`. |
| `outcomeIndex` | |
| `amount`       | USDC decimal string, as sent on create. |
| `side`         | `buy` or `sell`. |
| `status`       | See the table above. |
| `metadata`     | The tags from the create call (`{}` if none). Use them to route events without a lookup. |

### `trade.confirmation-required`

Adds `confirmationExpiresAt`, the time the confirmation token expires (60 seconds after the trade was created). The token itself is never sent in a webhook; it is only in the `202` response to `POST /v1/trades`.

### `trade.completed`

Adds `txHash` (a base58 Solana signature, or an EVM `0x` hash on an EVM market) and `tokensOut` (outcome tokens received, an 18-decimal integer string).

### `trade.failed` and `trade.rejected`

Add `errorCode` and `errorMessage`. `errorMessage` is sanitised. `errorCode` is a lowercase outcome code, which is a different namespace from the REST API's error codes:

`account_not_found`, `insufficient_balance`, `wallet_invalid`, `wallet_not_delegated`, `market_closed`, `market_settled`, `market_not_found`, `no_matching_market`, `slippage`, `trade_too_large`, `no_position`, `no_results`, `blockchain_error`, `rate_limit`, `circuit_breaker_open`.

Treat the list as open: handle unknown values generically.

## Headers

```
Content-Type:        application/json
User-Agent:          Kash-Webhooks/1.0
X-Kash-Signature:    t=1792000000000,v1=<hex-hmac-sha256>
X-Kash-Event-Id:     6f1c2a3b-9d0e-4f7a-8c1b-6e5d3f4a2c9b
X-Kash-Event-Type:   trade.completed
X-Kash-Api-Version:  2026-08-19
```

- `X-Kash-Signature`: the HMAC of the body. **Always verify it.** See [Verifying signatures](/developer-docs/rest-api/webhooks/verifying).
- `X-Kash-Event-Id`: same as the body's `id`.
- `X-Kash-Event-Type`: same as the body's `type`.

## Delivery semantics

- **At least once.** An event can arrive more than once. Make your handler idempotent by deduplicating on the event id.
- **In order per key.** Events for one API key are delivered one at a time, in order. A failing event holds back later events for the same key until it is delivered or its attempts run out.
- **Respond quickly with a `2xx`.** Each attempt times out after **10 seconds**. Do slow work after you respond.
- **Retries** happen automatically for timeouts, network errors, `5xx` and most `4xx` responses. Responding `400`, `404`, `410` or `422`, or with a redirect, stops delivery of that event. See [Retries & redelivery](/developer-docs/rest-api/webhooks/retries).

## Inspecting deliveries

`GET /v1/webhooks/events` lists the key's events with their delivery state:

```bash
curl 'https://api.kash.bot/v1/webhooks/events?status=failed&limit=10' \
  -H "X-API-Key: $KASH_API_KEY"
```

Each trade also carries a `webhookDelivery` summary on `GET /v1/trades/{id}`.

## A minimal receiver

```ts
import express from 'express';
import { KashClient, KashWebhookSignatureError } from '@kashdao/sdk';

const app = express();
const kash = new KashClient({ apiKey: process.env.KASH_API_KEY! });

app.post('/webhooks/kash',
  // Verify against the RAW body: re-serialised JSON will not match the signature.
  express.raw({ type: 'application/json' }),
  async (req, res) => {
    let event;
    try {
      event = await kash.webhooks.constructEvent(
        req.body.toString('utf8'),
        req.header('x-kash-signature') ?? '',
        process.env.KASH_WEBHOOK_SECRET!,
      );
    } catch (err) {
      if (err instanceof KashWebhookSignatureError) return res.status(400).send('bad signature');
      throw err;
    }

    if (await alreadyProcessed(event.id)) return res.status(200).send('ok');

    switch (event.type) {
      case 'trade.confirmation-required': /* … */ break;
      case 'trade.completed':             /* … */ break;
      case 'trade.failed':                /* … */ break;
      case 'trade.rejected':              /* … */ break;
    }
    await markProcessed(event.id);
    res.status(200).send('ok');
  },
);
```

Responding `400` to a bad signature stops retries of that request, which is right: a forged request should not be retried. To verify without the SDK, see [Verifying signatures](/developer-docs/rest-api/webhooks/verifying).
