Every data route on `api.kash.bot` requires an API key. Only `/v1/health`, `/v1/ready`, `/v1/openapi.json` and `/v1/docs` are open.

## The `X-API-Key` header

Send your key on every request as `X-API-Key`. Send exactly one: a request with two `X-API-Key` headers is refused.

```bash
curl https://api.kash.bot/v1/markets \
  -H "X-API-Key: kash_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx" \
  -H "X-Kash-Api-Version: 2026-08-19"
```

Keys are issued in the Kash app under **Settings → API Keys**. The plaintext is shown once. A user can hold at most **5 active keys**.

<Tip>
With [`@kashdao/sdk`](/developer-docs/rest-api/sdks/typescript) you don't set headers yourself. Construct the client with your key and it authenticates every request; a `kash_test_` key goes to staging and a `kash_live_` key to production.

```ts
import { KashClient } from '@kashdao/sdk';
const kash = new KashClient({ apiKey: process.env.KASH_API_KEY! });
```
</Tip>

## Key format

```
kash_live_<32 base62 characters>   # production
kash_test_<32 base62 characters>   # staging
```

The server stores only a keyed hash of each key, never the plaintext. **Never log or commit a key.**

## Scopes

Each key carries a set of scopes, and each route requires one. A key without the route's scope gets `403 INSUFFICIENT_SCOPE`.

| Scope             | Routes |
| ----------------- | ------ |
| `markets:read`    | `GET /v1/markets`, `GET /v1/markets/{id}`, `GET /v1/markets/{id}/predictions` and `GET /v1/markets/{id}/disputes` |
| `markets:quote`   | `GET /v1/markets/{id}/quote` |
| `portfolio:read`  | `GET /v1/portfolio`, `GET /v1/portfolio/positions` |
| `trades:read`     | `GET /v1/trades`, `GET /v1/trades/{id}`, `GET /v1/traces/{correlationId}` |
| `trades:write`    | `POST /v1/trades`, `POST /v1/trades/{id}/confirm`, `POST /v1/redemptions` and `POST /v1/markets/{id}/disputes` |
| `webhooks:manage` | `GET /v1/webhooks/events`, `POST /v1/webhooks/events/{eventId}/redeliver`, `POST /v1/auth/api-keys/me/webhook-secret/rotate` |
| `auth:manage`     | `GET /v1/account/usage` |

A key created without an explicit scope list gets `markets:read`, `markets:quote` and `portfolio:read`. Choose the scopes you need when you create the key, and no more: a read-only analytics key should never carry `trades:write`.

## Tiers

Each key has a tier, which sets its rate limit and spending caps. See [Rate limits](/developer-docs/rest-api/rate-limits) for the numbers.

| Tier         | How to get it |
| ------------ | ------------- |
| `free`       | Self-serve in the Kash app. |
| `developer`  | On request to [support@kash.bot](mailto:support@kash.bot). |
| `enterprise` | Issued by Kash. [Contact sales](mailto:sales@kash.bot). |
| `mm`         | Market-maker tier, issued by Kash. [Contact sales](mailto:sales@kash.bot). |

## Account status

A key belongs to the account that created it in the web app. If that account is suspended or closed, its keys are refused with `403 ORGANIZATION_INACTIVE`.

## IP allowlists

Optional, per key. When a key has an allowlist, a request from any other address is refused with `403 IP_NOT_ALLOWED` before the route runs. Entries are IPv4 or IPv6 addresses or CIDR ranges:

```
203.0.113.45, 198.51.100.0/24, 2001:db8::/32
```

Set it on the key in the Kash app. We strongly recommend an allowlist for production keys.

## Request signing (optional)

You can sign requests with an HMAC as a defence against tampering and replay of a captured request. Send `X-Kash-Signature` (exactly one) in the same format as webhook signatures:

```
X-Kash-Signature: t=<unix-ms>,v1=<hex-hmac-sha256>
```

- **Secret:** your API key plaintext, the value you send in `X-API-Key`.
- **Signed input:** `<t>.<METHOD>.<path>.<raw-body>`: the timestamp from `t=`, the HTTP method in upper case, the URL path **without** the query string, and the exact body bytes (empty for a `GET`).
- **Algorithm:** HMAC-SHA256, hex-encoded. Several `v1=` values are accepted; one must match.
- **Tolerance:** the timestamp must be within 5 minutes of the server's clock.

```ts
import { createHmac } from 'node:crypto';

const ts = Date.now();
const canonical = `${ts}.POST./v1/trades.${rawBody}`;
const sig = createHmac('sha256', apiKey).update(canonical).digest('hex');
// X-Kash-Signature: t=${ts},v1=${sig}
```

A present signature must verify: a mismatch, a malformed header or a stale timestamp is `401 REQUEST_SIGNATURE_INVALID`. Signing applies to every authenticated route. It is optional unless your key has been set to **require** signing, in which case an unsigned request is also refused with `401 REQUEST_SIGNATURE_INVALID`.

Because the signing secret is the key itself, signing protects body integrity and limits the replay window of a captured request. It does not protect you against a stolen key.

## Key rotation

Rotate a key when someone with access leaves, when a key may have been logged or committed, or as routine hygiene:

1. Create a new key in the Kash app.
2. Roll it out to your services.
3. Confirm the old key has gone quiet (`GET /v1/account/usage` with the old key shows no new trades).
4. Revoke the old key. Revocation takes effect immediately (`401 API_KEY_REVOKED`).

Keys can carry an expiry date; an expired key gets `401 API_KEY_EXPIRED`. API keys have no overlap window. Webhook *secrets* do: see [Secret rotation](/developer-docs/rest-api/webhooks/secret-rotation).

## Auth failures

| Status | `code`                      | Meaning |
| ------ | --------------------------- | ------- |
| 401    | `API_KEY_MISSING`           | No `X-API-Key` header. |
| 401    | `API_KEY_MALFORMED`         | Not a well-formed Kash key. |
| 401    | `API_KEY_INVALID`           | Key not recognised. |
| 401    | `API_KEY_REVOKED`           | Key revoked. |
| 401    | `API_KEY_EXPIRED`           | Key past its expiry. |
| 401    | `REQUEST_SIGNATURE_INVALID` | Signature present but invalid, or missing on a key that requires it. |
| 403    | `INSUFFICIENT_SCOPE`        | Key lacks the route's scope. |
| 403    | `ORGANIZATION_INACTIVE`     | The key's account is suspended or closed. |
| 403    | `IP_NOT_ALLOWED`            | Source address not on the key's allowlist. |

Failed authentication is counted per source address: too many failures in a short window lock that address out for a period, answered with `429 RATE_LIMIT_EXCEEDED` and a `Retry-After` header.
