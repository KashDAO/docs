---

The Kash REST API returns errors as
[RFC 7807](https://www.rfc-editor.org/rfc/rfc7807) Problem Details, with
`Content-Type: application/problem+json`. Every response carries a stable
`code` and a `type` URL that resolves to that code's page in this catalogue:

```json
{
  "type": "https://docs.kash.bot/developer-docs/api-errors/MARKET_NOT_TRADEABLE",
  "title": "Market not tradeable",
  "status": 409,
  "code": "MARKET_NOT_TRADEABLE",
  "detail": "Market is frozen: its freeze deadline has passed and trading has closed.",
  "instance": "/v1/trades",
  "requestId": "01HQGY8K2N3X4Z5C6D7E8F9G0H"
}
```

| Field       | Always present | Meaning                                                                                  |
| ----------- | -------------- | ---------------------------------------------------------------------------------------- |
| `type`      | yes            | Link to this code's documentation page                                                   |
| `title`     | yes            | Short, stable summary of the problem                                                     |
| `status`    | yes            | The HTTP status, repeated in the body                                                    |
| `code`      | yes            | The stable, machine-readable identifier. **Branch on this.**                             |
| `detail`    | usually        | Human-readable explanation of this occurrence. May change at any time; don't parse it   |
| `instance`  | yes            | The request path (and query) that failed                                                 |
| `requestId` | yes            | Correlation id for this request. Quote it to Kash support                                |

Some codes add **extension members** at the top level of the body, next to
the standard fields: for example
`inFlight` and `maxInFlight` on
[`TRADE_IN_FLIGHT_LIMIT_EXCEEDED`](/developer-docs/api-errors/TRADE_IN_FLIGHT_LIMIT_EXCEEDED),
`queueAgeSeconds` on
[`TRADE_ADMISSION_BUSY`](/developer-docs/api-errors/TRADE_ADMISSION_BUSY), and
`requested`, `supported` and `current` on
[`API_VERSION_UNSUPPORTED`](/developer-docs/api-errors/API_VERSION_UNSUPPORTED).
Each code's page documents its members.

Retryable errors (429, 503 and 504) carry a `Retry-After` header in
seconds. Rate-limited responses also carry `X-RateLimit-Limit`,
`X-RateLimit-Remaining` and `X-RateLimit-Reset`; see
[Rate limits](/developer-docs/rest-api/rate-limits). For how errors fit
the rest of the API, see [Errors](/developer-docs/rest-api/errors).

### Responses outside the catalogue

A few responses come from the API's framework layer rather than an
endpoint. They use the same problem shape but carry `type: "about:blank"`:
an unknown path returns `404` with `code: "ROUTE_NOT_FOUND"`, a request the
framework rejects before it reaches an endpoint can return `400` with
`code: "BAD_REQUEST"`, and a request that runs out of time returns
[`REQUEST_TIMEOUT`](/developer-docs/api-errors/REQUEST_TIMEOUT). Your
client should fall back to the HTTP status for any `code` it does not
recognise.

## Stability promise

The `code` field is part of the public API contract:

- **Adding a new `code`** is non-breaking. Your client should fall
  through to a generic handler for any code it doesn't recognise.
- **Renaming a `code`** is breaking and requires a new API version.
- **Repurposing a `code`** (changing what causes it) is breaking and
  requires a new API version.
- **Changing the HTTP status** of an existing `code` is breaking.

The `title` is also stable; it appears in customer logs and dashboards.
The `detail` string is **not** stable and may be reworded in any release.
`instance` and `requestId` are the fastest route to support: quote them
when you report a problem.

## Branching on errors

The TypeScript SDK (`@kashdao/sdk`) turns every problem response into a
typed error class, chosen from the HTTP status (and, for a few codes, the
`code`). Every class extends `KashError`, which exposes `code`,
`statusCode`, `requestId`, `isRetryable` and `extensions` (the extension
members above).

| HTTP status                       | SDK class                 |
| --------------------------------- | ------------------------- |
| 400, 422                          | `KashValidationError`     |
| 401                               | `KashAuthenticationError` |
| 403                               | `KashAuthorizationError`  |
| 404                               | `KashNotFoundError`       |
| 409, 410                          | `KashConflictError`       |
| 429                               | `KashRateLimitError`      |
| 503 (`ROUTE_DISABLED`, `API_TRADE_PROCESSING_HALTED`) | `KashMaintenanceError` |
| other 5xx (including 504)         | `KashServerError`         |

```ts
import {
  KashClient,
  KashAuthenticationError,
  KashConflictError,
  KashError,
  KashMaintenanceError,
  KashRateLimitError,
} from '@kashdao/sdk';

const kash = new KashClient({ apiKey: process.env.KASH_API_KEY });

try {
  await kash.trades.create({
    marketId: '3f6c1e2a-8d4b-4c7e-9a1f-2b5d6e7f8a9b',
    outcomeIndex: 0,
    amount: '100',
    side: 'buy',
  });
} catch (err) {
  if (err instanceof KashAuthenticationError) {
    // API_KEY_MISSING, API_KEY_INVALID, API_KEY_EXPIRED, ...: fix the key, don't retry
    throw err;
  }
  if (err instanceof KashRateLimitError) {
    // RATE_LIMIT_EXCEEDED or TRADE_IN_FLIGHT_LIMIT_EXCEEDED
    return scheduleRetry(err.retryAfterSeconds);
  }
  if (err instanceof KashMaintenanceError) {
    // ROUTE_DISABLED or API_TRADE_PROCESSING_HALTED
    return showUnavailableBanner(err.retryAfterSeconds);
  }
  if (err instanceof KashConflictError && err.code === 'MARKET_NOT_TRADEABLE') {
    return pickAnotherMarket();
  }
  if (err instanceof KashError) {
    // Any other API error: log the code and requestId for support
    console.error(err.code, err.requestId);
  }
  throw err;
}
```

By default the SDK retries 429 and 5xx responses (up to 3 retries, with
exponential backoff that honours `Retry-After`) and sends an
`Idempotency-Key` on every POST so retries cannot execute twice. Use
`KashError.isKashError(err)` instead of `instanceof` if errors may cross
a realm boundary (for example between a worker and the main thread).
