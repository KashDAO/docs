Every error the SDK throws extends `KashProtocolError` and carries a
stable string `code` (see the exported `ErrorCode`), structured
`context`, and `isRetryable` / `isOperational` flags. The Python SDK
uses the same class names and codes.

## Error classes

| Class                                | When it fires                                                                                                   | Retryable?                 |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------- | -------------------------- |
| `KashConfigError`                    | Invalid client config (`INVALID_CONFIG`) or a cluster with no Kash deployment (`UNSUPPORTED_CHAIN`)            | No                         |
| `KashValidationError`                | Bad input, or a trade the program would refuse, caught before signing. `programError` names the program error   | No                         |
| `KashSimulationRevertedError`        | The RPC's preflight simulation refused the transaction. `context.programError` names the program error          | No                         |
| `KashChainError`                     | RPC or on-chain failure. `code` says which (see below)                                                          | Check `isRetryable`        |
| `KashTransactionExpiredError`        | `TX_EXPIRED`: the blockhash expired and a status check found no trace of the signature, so it did not land      | Yes: rebuild and resend    |
| `KashTransactionOutcomeUnknownError` | `WAIT_RECEIPT_FAILED`: the transaction **may have landed**                                                       | **No**: look it up first   |
| `KashSignerError`                    | The signer failed or cannot sign (e.g. `SIGNER_UNSUPPORTED` for a disconnected wallet)                          | No                         |

Refusals checked before signing include `InvalidState` (market not
active) and a frozen market.

## Sending: which failures are safe to retry

| Outcome                                                        | Error                                         | What to do                                    |
| -------------------------------------------------------------- | --------------------------------------------- | --------------------------------------------- |
| Preflight simulation refused                                   | `KashSimulationRevertedError`                 | Fix the input (amount, slippage, market)      |
| RPC refused the send before forwarding it                      | `KashChainError` `TX_SEND_FAILED` (retryable) | Rebuild and resend                            |
| Blockhash expired and the transaction did not land             | `KashTransactionExpiredError` (retryable)     | Rebuild with a fresh quote and resend         |
| Landed and failed on chain                                     | `KashChainError` `TX_REVERTED`                | Inspect `context.programError`                |
| Anything else: timeout, HTTP error (429 included), unreadable confirmation | `KashTransactionOutcomeUnknownError` | Look up `signature` before doing anything    |

Every error raised after signing carries the transaction signature
(`context.signature`, and `.signature` on the two transaction error
classes), computed before the send.

<Warning>
`WAIT_RECEIPT_FAILED` is deliberately **not** retryable. Rebuilding takes a
fresh blockhash, which makes a new transaction; if the first one landed,
sending both doubles the trade. Check the signature's status first.
</Warning>

## Canonical handling

Use the static `is()` guards rather than `instanceof`; they work across
module copies and bundles.

```ts
import {
  ErrorCode,
  KashChainError,
  KashSimulationRevertedError,
  KashTransactionExpiredError,
  KashTransactionOutcomeUnknownError,
  KashValidationError,
} from '@kashdao/protocol-sdk/solana';

try {
  await kash.trades.buy({ market: 5n, outcome: 0, amountUsdc: 1_000_000n, maxSlippageBps: 100, signer });
} catch (err) {
  if (KashValidationError.is(err)) {
    // Refused before signing: nothing was sent.
    console.error('refused:', err.programError ?? err.message);
  } else if (KashSimulationRevertedError.is(err)) {
    console.error('preflight refused:', err.context?.['programError'] ?? err.message);
  } else if (KashTransactionOutcomeUnknownError.is(err)) {
    // May have landed. Look the signature up before retrying.
    console.error('outcome unknown:', err.signature);
  } else if (KashTransactionExpiredError.is(err)) {
    // Did not land. Safe to rebuild with a fresh quote and resend.
  } else if (KashChainError.is(err) && err.code === ErrorCode.TX_SEND_FAILED) {
    // The RPC refused it before forwarding. Safe to resend.
  } else {
    throw err;
  }
}
```

## Reads

A position or token account that does not exist reads as a balance of
zero, because the program creates neither until there is something to
hold. A market, config or template that does not exist is an error
(`ACCOUNT_NOT_FOUND`), and an account owned by a different program
(wrong cluster or program id) is `ACCOUNT_OWNER_MISMATCH`. An RPC failure
is a retryable `KashChainError`, never a zero.

## `isOperational` and `isRetryable`

`isOperational: true` means a known failure mode: the input or the
chain state is the cause. `isRetryable: true` means a fresh attempt may
succeed without changing the input. The flags are independent: a
simulation refusal is operational but not retryable.
